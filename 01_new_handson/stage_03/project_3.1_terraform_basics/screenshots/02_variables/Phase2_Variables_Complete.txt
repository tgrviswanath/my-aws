PART A  TOOL THEORY: TERRAFORM VARIABLES


A1. What is Infrastructure as Code (IaC)?


  Traditional Way (Before IaC):
    Engineer logs into AWS Console
    clicks through menus manually
    creates EC2, S3, RDS by hand
    no record of what was done
    cannot repeat it exactly
    team cannot review it
    disaster recovery = start from scratch

  Infrastructure as Code (IaC):
    Engineer writes a .tf file
    describes the desired infrastructure
    commits to Git (version controlled)
    team reviews via Pull Request
    Terraform creates it automatically
    same result every single time
    disaster recovery = terraform apply


A2. What is Terraform?


  Created by  : HashiCorp (2014)
  Type        : Open-source Infrastructure as Code tool
  Language    : HCL (HashiCorp Configuration Language)
  Runs on     : Your local machine or CI/CD server
  Talks to    : AWS, Azure, GCP, Kubernetes, 1000+ providers

  Terraform is NOT:
    An AWS service (it runs locally on your machine)
    A programming language
    Only for AWS (works with any cloud)

  Terraform IS:
    A CLI tool you install on your machine
    Declarative  you describe WHAT, not HOW
    State-aware  tracks what it created
    Provider-based  plugins for each cloud
    The industry standard for IaC


A3. What Are Terraform Variables?


  Variables make Terraform configurations REUSABLE.
  Instead of hardcoding values, you pass them in.

  Without variables (hardcoded):
    resource "aws_s3_bucket" "main" {
      bucket = "dev-my-app-data-495331821583"   hardcoded!
    }
    Problem: To deploy to qa, you must edit the code.

  With variables:
    resource "aws_s3_bucket" "main" {
      bucket = "${var.environment}-${var.bucket_name}"
    }
    Solution: Change dev.tfvars to qa.tfvars  no code changes!


A4. Variable Types in Terraform


  Type              Example                          Use case
  
  string            region = "ap-south-1"            Text values
  number            port = 8080                      Numeric values
  bool              enable_versioning = true         Feature flags (on/off)
  list(string)      ["us-east-1", "ap-south-1"]      Multiple values
  map(string)       { Owner = "vswnth1" }            Key-value pairs
  object            { name = string, age = number }  Structured data
  any               accepts any type                 Flexible inputs


A5. Variable Declaration Syntax


  variable "bucket_name" {
    description = "S3 bucket name (must be globally unique)"
    type        = string
    default     = "my-default-bucket"   optional

    validation {                         optional
      condition     = length(var.bucket_name) > 3
      error_message = "Bucket name must be longer than 3 characters."
    }
  }

  Parts explained:
    description  : Human-readable explanation (shown in prompts)
    type         : Enforces the data type
    default      : Used if no value is provided
    validation   : Rejects invalid values BEFORE touching AWS


A6. 3 Ways to Pass Variable Values


  Way 1  .tfvars file (RECOMMENDED for real projects)
    terraform plan -var-file="dev.tfvars"
    All values loaded from file
    One file per environment: dev.tfvars, qa.tfvars, prod.tfvars

  Way 2  Runtime override (-var flag)
    terraform plan -var-file="dev.tfvars" -var="environment=qa"
    Overrides a single value at runtime
    Useful for quick one-off changes

  Way 3  Interactive prompt (no flags)
    terraform plan
    Terraform stops and asks for missing required values
    NEVER use in CI/CD pipelines  blocks automation

  Way 4  Environment variables (TF_VAR_)
    export TF_VAR_bucket_name="my-bucket"
    terraform plan
    Useful in CI/CD when you can't use files


A7. Variable Validation


  validation {
    condition     = contains(["dev", "qa", "prod"], var.environment)
    error_message = "Environment must be dev, qa, or prod."
  }

  Benefits:
    Catches invalid values BEFORE connecting to AWS
    Saves time and prevents mistakes
    Self-documenting  shows allowed values in error message
    Works at plan time  no resources created on failure


A8. Common Terraform Commands (Variables Context)


  Command                                    Purpose
  
  terraform plan -var-file="dev.tfvars"      Plan with tfvars file
  terraform apply -var-file="dev.tfvars"     Apply with tfvars file
  terraform destroy -var-file="dev.tfvars"   Destroy with tfvars file
  terraform plan -var="key=value"            Override single variable
  terraform plan                             Interactive prompt for missing vars
  terraform output                           Show output values after apply
  terraform output -raw bucket_name          Get clean value for scripts


A9. .tfvars File Best Practices


  File naming convention:
    dev.tfvars    development environment
    qa.tfvars     quality assurance environment
    prod.tfvars   production environment

  What to put in .tfvars:
    Environment-specific values (region, sizes, counts)
    Non-sensitive configuration

  What NOT to put in .tfvars:
    Passwords, API keys, secrets
    Use AWS Secrets Manager or environment variables instead

  Git rules:
    COMMIT:   dev.tfvars, qa.tfvars (non-sensitive)
    NEVER:    prod.tfvars with real passwords
    ALWAYS:   Add *.tfvars to .gitignore if they contain secrets

PART D  THE FILES


D1. main.tf


  File location:
    D:\1.projects\AI\my-aws\01_new_handson\stage_03\
    project_3.1_terraform_basics\02_variables\main.tf

  File contents:

    terraform {
      required_providers {
        aws = { source = "hashicorp/aws", version = "~> 5.0" }
      }
    }

    provider "aws" { region = var.region }

    variable "region" {
      description = "AWS region"
      type        = string
      default     = "ap-south-1"
    }

    variable "bucket_name" {
      description = "S3 bucket name (must be globally unique)"
      type        = string
      # No default  will prompt at runtime
    }

    variable "environment" {
      description = "Deployment environment"
      type        = string
      default     = "dev"
      validation {
        condition     = contains(["dev", "qa", "prod"], var.environment)
        error_message = "Environment must be dev, qa, or prod."
      }
    }

    variable "enable_versioning" {
      description = "Enable S3 versioning"
      type        = bool
      default     = true
    }

    variable "tags" {
      description = "Tags to apply to all resources"
      type        = map(string)
      default = {
        Project   = "handson"
        Stage     = "stage-03"
        ManagedBy = "terraform"
      }
    }

    resource "aws_s3_bucket" "main" {
      bucket = "${var.environment}-${var.bucket_name}"
      tags   = merge(var.tags, { Environment = var.environment })
    }

    resource "aws_s3_bucket_versioning" "main" {
      bucket = aws_s3_bucket.main.id
      versioning_configuration {
        status = var.enable_versioning ? "Enabled" : "Suspended"
      }
    }

    output "bucket_name"   { value = aws_s3_bucket.main.bucket }
    output "bucket_arn"    { value = aws_s3_bucket.main.arn }
    output "environment"   { value = var.environment }

  What changed with just ONE flag:
    Way 1 (dev.tfvars)          Way 2 (-var override)
    
    bucket: dev-my-app-data-... bucket: qa-my-app-data-...
    Environment tag: "dev"      Environment tag: "qa"
    Code changed: NO            Code changed: NO

  Key learning:
    -var flag overrides any value from .tfvars at runtime.
    Same main.tf, same dev.tfvars  just one flag changed everything.
    This is exactly how real companies deploy to multiple environments.
