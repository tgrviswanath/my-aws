The Problem

Project 3.2 worked.
But it didn't scale.

❌ Project 3.2 (flat)

  • All resources in one folder
  • To deploy qa — copy-paste everything
  • Bug fix? Update in every environment
  • One state file for everything
  • No reuse, no isolation

✅ Project 3.3 (modules)

  • 3 reusable modules: vpc, ec2, rds
  • Deploy qa — just call the same modules
  • Bug fix? Update the module once
  • Separate state per environment
  • DRY — Don't Repeat Yourself

Module Wiring

Modules talk to each other
through outputs.

# environments/dev/main.tf module "vpc" { source = "../../modules/vpc" vpc_cidr = "10.0.0.0/16" azs = ["ap-south-1a", "ap-south-1b"] } module "ec2" { source = "../../modules/ec2" vpc_id = module.vpc.vpc_id ← output from vpc module public_subnet_ids = module.vpc.public_subnet_ids } module "rds" { source = "../../modules/rds" vpc_id = module.vpc.vpc_id app_sg_id = module.ec2.app_sg_id ← output from ec2 module }

Key Learnings

What Terraform modules
actually give you.

  • 1
    DRY infrastructure — vpc, ec2, rds modules written once, deployed to dev and qa with zero duplication
  • 2
    Module namespacing in state — module.vpc.*, module.ec2.*, module.rds.* — clear ownership
  • 3
    State isolation — each environment has its own terraform.tfstate. Changes to dev never touch qa
  • 4
    Module outputs wire modules together — module.ec2.app_sg_id passed directly into the rds module
  • 5
    CIDR planning matters — dev=10.0.x.x, qa=10.1.x.x, prod=10.2.x.x — no overlap, safe to VPC peer later
