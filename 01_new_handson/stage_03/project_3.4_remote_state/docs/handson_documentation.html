1 Project Overview

What this project does and why remote state matters

This project demonstrates how to move Terraform state from a local file to Amazon S3 with DynamoDB locking — the industry-standard setup for team-based infrastructure management. It also covers reading outputs across Terraform configurations using terraform_remote_state, live state migration, and importing existing AWS resources.

Why Remote State Matters

Two people apply at once → corruptionDynamoDB lock prevents concurrent applies

State lost if laptop diesS3 versioning keeps full history
Secrets visible in local fileS3 encryption at rest (AES-256)

4 Code Review & Fixes

Issues identified and corrected before execution

Before running any Terraform commands, a full code review was performed across all configuration files. Three issues were found and fixed:

FIX 1
State key mismatch — remote_state_consumer/main.tf

main/main.tf writes state to stage-03/project-3.4/main/terraform.tfstate but the consumer was pointing to stage-03/project-3.4/terraform.tfstate — it would never find the state file.

Fix: Updated consumer key to match stage-03/project-3.4/main/terraform.tfstate.

FIX 2
Non-existent output reference — remote_state_consumer/main.tf

Consumer referenced outputs.vpc_id which was never defined in main/main.tf. Would fail at plan time.

Fix: Replaced with the 4 actual outputs: app_bucket_name, app_bucket_arn, account_id, region.

FIX 3
Duplicate backend block — main/main.tf + main/backend.tf

Both files had a terraform { backend "s3" {} } block. Two terraform blocks in the same directory causes a conflict.

Fix: Removed backend block from main.tf, kept it only in backend.tf (conventional pattern).

FIX 4
Inline provider syntax error — main/main.tf, remote_state_consumer/main.tf

Inline { source = "..." version = "..." } missing separator between attributes. Terraform requires newline or comma.

Fix: Expanded to multi-line format with source and version on separate lines.

✅ Everything else was correct bootstrap/main.tf was clean. DynamoDB LockID hash key was exact. Provider versions consistent (~> 5.0). S3 bucket naming pattern consistent. Encryption, versioning, public access block all properly configured.

8 Phase 4 — DynamoDB Locking

Observed automatically on every plan and apply

DynamoDB locking was observed on every single Terraform operation throughout this hands-on. No separate test was needed — it was working from the first apply.

Acquiring state lock. This may take a few moments... ... terraform operation runs ... Releasing state lock. This may take a few moments...

How It Works

StepWhat Happens
1. terraform plan/apply startsTerraform writes a lock item to DynamoDB with LockID = state key path
2. Second apply tries to runDynamoDB ConditionalCheckFailedException — lock already exists
3. First apply finishesLock item deleted from DynamoDB
4. Second apply can proceedAcquires lock, runs safely
Stuck Lock Recovery If terraform apply crashes mid-run, the lock may not be released. Use: terraform force-unlock <LOCK_ID> or the state_manager.py unlock command to remove it manually.

9 Phase 5 — Remote State Consumer

Reading outputs from main/ across configs using terraform_remote_state

📁 Working Directory: remote_state_consumer/

How It Works

The consumer config has no resources of its own. It uses the terraform_remote_state data source to read the outputs that main/ wrote into S3 state.

data "terraform_remote_state" "main" {
  backend = "s3"
  config = {
    bucket = "handson-terraform-state-495331821583"
    key    = "stage-03/project-3.4/main/terraform.tfstate"
    region = "us-east-1"
  }
}

output "app_bucket_name_from_remote_state" {
  value = data.terraform_remote_state.main.outputs.app_bucket_name
}

13 Cleanup & Destroy

Teardown order and steps

⚠️ Order matters Bootstrap must be destroyed LAST — it holds the S3 bucket that stores all other state files. Destroying it first would orphan all other state.

Special Step — Empty S3 Bucket Before Bootstrap Destroy

Because S3 versioning was enabled, the bucket contains versioned state files. AWS requires all versions to be deleted before the bucket can be removed.

# Create delete_versions.json with all version IDs, then:
aws s3api delete-objects --bucket handson-terraform-state-495331821583 \
  --delete file://delete_versions.json

# Then destroy bootstrap
terraform destroy -auto-approve

Remove prevent_destroy Before Bootstrap Destroy

The state bucket had lifecycle { prevent_destroy = true } — this must be removed from bootstrap/main.tf before running destroy, otherwise Terraform will refuse to delete it.

14 Key Takeaways

Lessons learned from this hands-on

🪣 Bootstrap is One-Time

The S3 bucket and DynamoDB table are created once and kept permanently. Never destroy the state bucket — it holds all your infrastructure history. Use prevent_destroy = true in production.

🔒 Locking is Automatic

DynamoDB locking happens on every plan and apply without any extra configuration. Every operation acquires and releases the lock automatically.

🔗 Cross-Config Sharing

terraform_remote_state lets teams share infrastructure outputs (VPC IDs, subnet IDs, bucket names) without coupling their code or giving access to each other's configs.

🚀 Migration is Simple

Migrating from local to remote state is just: add backend block → terraform init → type yes. Terraform handles copying the state automatically.

📥 Import Pattern

To import existing resources: write a matching resource block → terraform import → verify with terraform plan showing 0 changes. Config must match reality exactly.

🗂️ State Key Strategy

Use a consistent path convention for state keys: stage/project/env/terraform.tfstate. This keeps all state files organized in one bucket across all projects.

Common Pitfalls

PitfallSolution
Two terraform blocks in same directoryKeep backend in backend.tf, required_providers in main.tf
Inline provider syntax missing separatorUse multi-line format with source and version on separate lines
Consumer referencing non-existent outputAlways check what outputs the source config actually exports
State key mismatch between writer and readerCopy-paste the exact key from backend.tf into the consumer config
S3 bucket not empty on destroyDelete all versions and delete markers before terraform destroy
prevent_destroy blocks teardownRemove lifecycle block before running destroy in dev/test environments
Wrong region in providerAlways confirm your AWS CLI default region before writing configs
